# engine/simulation/stages

One file per pipeline stage, in this order: `address`, `dns`, `port`, `route`, `firewall-out`, `forward`, `firewall-in`, `host`, `app` (in `web/`, only for a packet that carries a message), `reply`. A stage reads and extends the simulation context and says whether the packet continues.

- `route` decides, before any firewall, where a packet from an office device goes (RFC 1122, §3.3.1.1): to the device itself (loopback, its own IP), straight into its own LAN, or to its default gateway when the destination is in another LAN of the office. It reads that from the routing table of the device (`chooseRoute`: the connected row of its LAN or its default row, the longest range wins) and records the decision in `ctx.routes` when it hands the packet to the network; that is data for `Trace.routes`, not a step. A device with no cable, or with no gateway for a destination outside its LAN, ends as `no-route` with no warning. In a VPC, and for an actor, `route` also settles the destination, as before.
- `dns` is built by `createDnsStage(send)`, so it does not import the pipeline that contains it: `simulate.ts` hands it `sendQuestion`, which runs the question as a datagram of the same send (with its NAT table, its port counters and its second). A device of an office looks a name up the way the packet says (`PacketSpec.lookup`). The system (`ping`, `nc`, the default) reads the hosts file of the device first: a line for the name writes `dns-hosts-file`, sends nothing and leaves the cache as it was. Otherwise it asks with `resolve` (`src/engine/dns/`), measured against `ctx.now` and the cache in `ctx.dnsCache`; the question it sent is kept in `ctx.question` (data for `Trace.question`, with the answer as a `dig` carries it) and writes no step of its own, and the stage writes one step: `dns-answered` or `dns-cached` (the same answer, from the cache of the resolver), `dns-nxdomain`, `dns-servfail`, `dns-no-address`, `dns-resolver-silent` (the question never reached a host, so no resolver spoke), `dns-no-resolver` (a host got the question and did not answer it as a resolver, which the step names) or the old `dns-unresolved` when the device has no resolver; whatever a resolver answers goes into `ctx.dnsCache`, so the cache goes on to the next send. A `dig` writes no step: it reads no hosts file and its destination is the resolver, so the stage sets `ctx.destIp` to the `dnsServer` of the device and `ctx.asking` to the name, and the datagram goes through the other stages like any packet; `simulate.ts` takes the answer when the trip ends. With no `dnsServer` a `dig` ends like any lookup with none (`dns-unresolved`). Every other sender resolves EC2 names as it always did. The result is also `ctx.dns`, data for `Trace.dns`.
- `port` gives a TCP or UDP packet that has no source port the next one of its sender (`ctx.nextSourcePort`, the counter that `Carried` hands from one send to the next) and moves that sender on by one; a packet with its own port keeps it and the counter stays, and an ICMP message has none. It runs after `dns`, when the destination is an IP, so a send that ended before (an address that is not valid, a name nobody resolved) took no port; the question of a lookup by name has taken its own from the same counter by then, so the packet gets the next one. It writes no step.
- `forward` delivers what `route` handed over (`ctx.delivery`), after the sender's outbound firewall. It finds a connected owner of the IP in the sender's LAN. Nobody owns it: the sender's own device warns (`unreachable`, a `host-unreachable` notice from the sender), unless an outbound firewall silenced the packet first. The router of the sender's LAN, the gateway or the owner of the IP, takes the packet over in `paths/routers.ts` (TTL, hops, warnings, the road to the server). The gateway is any other device: it drops the packet in silence (`timeout`). A packet `route` already settled passes through, and `forward` writes a step only when it stops the packet or when a router passes it on (`forward-hop`). It also records the sender's LAN as the first leg of the trip (`addLeg`), for the round trip time, once someone in that LAN takes the packet.
- `route` also takes a packet that a client actor of the internet sends to an office with routers to the router that owns the public IP (`ctx.entry`), or ends it as `lost` when none does; `forward` enters that router first, and the router decides what it is (a router that answers for itself, or the NAT: `src/engine/simulation/CLAUDE.md`).
- `route` also hands a destination outside the office to the default gateway when the office has routers (`route-leaves-office`); with no routers it keeps the old behavior.
- `host` and `reply` serve a device and a responder (a router answering for its own interface, or a server of the internet) the same way, through `receiverOf`. `host` finds a TCP or UDP service by protocol, port and destination IP (`lookupService`): a service, a closed port, a service on another address and a service whose process stopped are four different outcomes (accepted, `host-refused` or `host-udp-closed`, `host-wrong-address` and `process-stopped`). For TCP the last three are an RST and end as `refused`; for UDP they are an ICMP Port Unreachable from the host itself (`rejectUdp`, with `sendNotice`) and end as `unreachable`. `firewall-in` lets a packet pass when it reached no device.
- `host` and `reply` also say what the ends of a TCP or UDP exchange said (`sayRefusal` and `sayAnswer`, in `context.ts`), in `ctx.exchange`, which `simulate` seeds with the opening (SYN or query). That is data for `Trace.exchange`, not a step: no stage writes a step for it.

- `nat.ts` is not in the pipeline: a stage runs once per packet, in order, and the NAT acts where a router meets the packet, in the middle of `forward`. When the router sends the packet out of the office it calls `translateOnExit`, which reads the context (`ctx.nat`, `ctx.packet`, the source) and the rules of `src/engine/nat/`, and leaves `ctx.translation` and the new `ctx.nat`. When a packet from outside comes in for its public IP it asks `entersNat` (is this router the NAT for this packet?) and then calls `translateOnEntry`, which looks for a forward or a row and leaves `ctx.translation` and `ctx.delivered`. Neither writes a step: the router that calls them writes `nat-forwarded` or `nat-no-translation`, and only for a packet from outside, so the steps of every other trace are the same.

- A new network mechanic (for example NACL) adds a stage here and registers it in the pipeline of `src/engine/simulation/simulate.ts`.
