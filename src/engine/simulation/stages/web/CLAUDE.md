# engine/simulation/stages/web

The `app` stage (`app.ts`): the web service at the end of the connection. It runs after `host` and before `reply`, and only for a packet that carries a message; a packet with no message meets no `app` stage, writes no step and has no `Trace.app`.

- `run` gives a packet with a message `ctx.app = { request }` before any stage runs, built from the message alone, so `Trace.app.request` exists for every packet that carries one, whether or not the connection opened. `Trace.app.response` exists only when a web service answered. A packet that was refused, dropped by a firewall, unresolved or lost has a request and no response, and the `app` stage never ran.
- The stage finds the TCP service that accepted the packet (`acceptingService`). A service with no `web` accepts the connection and says nothing in HTTP: the stage adds the SYN-ACK and the ACK to the exchange (the connection did open) and ends the trip as `arrived-no-reply`, with no step and no response.
- A web service chooses its site by the host of the request (`chooseSite`): the step `web-site-chosen` when a site has that name, `web-default-site` when it serves the default site (the name is in the reason, a name or an IP). The orders are read from `ctx.apps` or from the starting orders of the site, `answerRequest` answers, and a change in the orders goes back to `ctx.apps` (`Carried.apps`) and the sessions the app opened to `ctx.sessions` (`Carried.sessions`). When a page that asks for a role answered 401 or 403 (`Answer.denial`; the 401 of a failed login writes none, because the login page asks for no role), a step `web-needs-login` (with the path) or `web-forbidden` (with the path and the user) comes next, `info` like the choice of the site, and says why. The last step is `web-answered` with the status code of the response. Both steps are `at` the device or server that answered. The trip then goes on to `reply`, which writes `reply-stateful` and ends it as `replied`: the reply of an HTTP exchange is never stopped by a firewall, because the firewalls check the request only.
- A site that forwards the path of the request (`originOf`, `src/engine/web/proxy/`) does not answer it: after `web-site-chosen` or `web-default-site` the stage sends a second packet, a TCP packet of the same message from the server of the proxy to the first origin of the site (`passThrough`, through `SendUpstream`, which `simulate.ts` hands it as `sendUpstream`, as `sendQuestion` is handed to the `dns` stage), with the method, path, query and body of the request, the `Host` of the client and the rest of its headers, and `X-Forwarded-For` with the IP of the client the proxy sees (the public IP of the NAT when the client is a device of the office). That packet crosses the pipeline like any other, from a server of the internet to another one (`route` delivers it with no firewall and no NAT in between), and its whole trace is kept as `Trace.app.upstream`; the orders, the sessions and the source-port counter it leaves go on with the send that forwards it. When the origin answered, the proxy writes its own `web-answered` with the same code, passes the response back as it came (same status, headers and body) and `Trace.app.generatedBy` is the one of the origin. When it did not (a first stand-in until the proxy generates its own codes), the trip ends as `arrived-no-reply` with the connection open and the trace has an `upstream` and no `response`.
- `Trace.app.generatedBy` is `{ id, role }`: the device or server whose app generated the code and `app`, or `proxy` for a code the proxy itself generated (none yet). A site that answers itself writes the id of its own server with the role `app`. It exists where `response` does.
- A message with `browser: true` is the only one that keeps cookies. `run` adds to its request the `Cookie` header with what the browser of the sending device holds for the host of the url (`withBrowserCookies`, so the trace shows it even when the connection never opened), and when the response sets a cookie the stage keeps it for that device and that host in `ctx.browser` (`Carried.browser`). Any other message carries a cookie only if its headers say so, and keeps none.
