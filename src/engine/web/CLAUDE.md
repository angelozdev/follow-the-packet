# engine/web

What a web service answers when a client speaks HTTP inside a TCP connection. Pure functions over data: the url, the request, the response, the choice of a site by the Host header and the pages and orders of an app. The stage that calls them is `src/engine/simulation/stages/web/app.ts`. An HTTP message is not a packet: it travels in the data of the TCP connection that the three-way handshake opened, so the packet keeps its TCP shape and carries the message in `PacketSpec.message`.

- `schema.ts`: `httpMessageSchema` (the request a client makes: `method` GET, POST or PUT, an absolute `http` or `https` `url`, optional `headers` and `body`; the Host header and the length of the body are never given) and `webServiceSchema` (`Service.web`: `sites` and `defaultSiteId`). A site is `{ id, names, pages, notFoundBody, orders? }`; a page is `{ path, methods, handler }` with the handlers `fixed` (a `body`), `order-read`, `order-create` and `order-replace`; `orders` is the order book `{ template, start }`. The schema asks that the default site be one of the sites, that no two sites share an id, that every name of a site go under `.example` (the name reserved for documentation, RFC 2606 §2, so no name of the game is a real one) and that a site with a page that serves orders have an order book. `siteContentSchema` is a site without its `id` and `names` (what a chip of a table of sites says it serves). `addSite` (`src/engine/network/actions.ts`) adds a site to a service and refuses a name that already has one. `networkSchema` asks that a web service be on a TCP service.
- `url.ts`: `parseUrl` gives scheme, host (a name or an IP), port (80 for `http` and 443 for `https` when the url gives none, RFC 9110 §4.2.1 and §4.2.2), path and query string without its `?`, and drops the fragment (`#…` never reaches the server, RFC 9110 §7.1). It is `URL` of the platform, so the host comes in lower case and a path is percent-encoded. `hostHeaderOf` is the value of the Host header (the host, and `:port` when the port is not the default of the scheme, RFC 9110 §7.2) and `targetOf` the path with its query. The rule that the Host header names the port only when it is not the default of the scheme is the ruling of the chapter 3 plan; the task that prints the output of `curl` checks it against the source of `curl` 8.21.0.
- `messages.ts`: `requestOf(message)` builds the request as it travels (`startLine`, `method`, `host`, `path`, `query`, `headers`, `body`). Its headers are Host first, then the headers the message brings, then `Content-Length` in bytes when there is a body. It does not add `User-Agent` or `Accept`: what a real `curl` sends is read from its source in the task that prints its output. `responseOf(statusCode, body)` builds a response with only `Content-Type` (`text/plain; charset=utf-8`) and `Content-Length` (simplification declared in the chapter 3 spec: a real server sends more). The length counts bytes (`byteLength`), not characters. The status codes are the two the app of block 1 uses, 200 and 404; each later block adds the ones it needs.
- `app.ts`: `chooseSite(web, host)` picks the site whose `names` include the host of the request, compared as DNS names (`sameName`), and otherwise the default site; `named` says which. The IP the request went to plays no part, and a name that went through a CNAME arrives as the url wrote it. `answerRequest(site, orders, request)` finds the page with the path and the method of the request (exact match; none is a 404 with the `notFoundBody` of the site, which also answers a method the path does not accept) and runs its handler: `fixed` answers 200 with its body; `order-read` reads the order whose `id` the query gives; `order-create` adds the next order (the highest id plus one) with the body as its content; `order-replace` sets the content of the order whose `id` the query gives. Every order handler answers 200 with the order written by the `template` of the book (`{id}` and `{content}`), and an `id` that is not a number or names no order is a 404. The engine writes no sentence: the template, the starting orders and every body, the 404 included, come from the data of the app, which the incident writes. `appKey` names the orders of a site in `Apps`, the state `Carried.apps` hands from one send to the next; an app with no entry has the `start` orders of its book.
- The orders of an app live in `Carried.apps`, so a `simulate` alone knows nothing of the sends before it. A move that changes the world clears the sends and with them the orders; that rule belongs to the session, not here.
- Not here: the stage and the trace (`src/engine/simulation/`), the model of the network (`src/engine/network/`), the Spanish text of the reasons (`src/copy/web/`).
- May import: `zod` and other files of `src/engine/`.
