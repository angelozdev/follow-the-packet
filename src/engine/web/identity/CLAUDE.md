# engine/web/identity

Who a request says it comes from, and whether that user may enter a page, and what a browser remembers of the sites it visits. Pure functions over the headers of a request, the users of a site and the cookies of a device; the page that asks for a role, the login and the answers 401 and 403 are built in `../app.ts`.

- `basic-credential.ts`: the Basic credential of RFC 7617. `basicAuthorizationHeader('user:password')` is the `Authorization` header a client sends (`Basic` and the base64 of that text in UTF-8, from `btoa` and `TextEncoder` of the platform), `credentialOf(headers)` reads it back (split on the first colon, as `curl` does; nothing when the header is missing, is not Basic, is not valid base64 or UTF-8, or has no colon) and `basicChallenge(realm)` is the `WWW-Authenticate` value of a 401 (`Basic realm="<realm>"`, RFC 7617 §2). The engine does not know a `curl`: the session writes the `Authorization` header into the message of a `curl -u` with `basicAuthorizationHeader` (`sentPacketFromChips`, `src/levels/contract/chips.ts`).
- `access.ts`: `denialOf(accounts, role, headers, sessionUsers)` decides for a page that asks for a `role`. The user is the one whose user and password the `Authorization` header presents or, when it presents none that is valid, the one of the session its `Cookie` names. A request whose user has the role gets nothing back (the page answers). A request with no user (no credential, a wrong password, a user the site does not have, a session that was never opened) gets `{ kind: 'needs-login' }` (a 401); a user without the role gets `{ kind: 'forbidden', user }` (a 403). The same request always gets the same decision. `loginUserOf(accounts, body)` is the user whose `usuario` and `clave` a login form gives.
- `cookies.ts`: the cookie of the game is a name and a value, with no attributes (`Secure`, `HttpOnly`, `SameSite`, expiry and domain are for chapter 20). `cookiesOf` reads the pairs of a `Cookie` header (`a=1; b=2`) or the first one of a `Set-Cookie`.
- `sessions.ts`: the session `s<n>` of an app is its n-th, the user it was opened for (`SessionUsers`; `Sessions` holds them by `appKey` in `Carried.sessions`). `sessionCookieOf(n)` is the `Set-Cookie` value `sesion=s<n>` and `sessionUserOf` the user a `Cookie` header names. The value follows the order of the sessions opened since the world last changed, so the same sends always give the same cookies.
- `browser-memory.ts`: what a browser holds, by the id of the device, as `{ site, name, value }` (the site is the host the url wrote, a name or an IP, never its port). `withBrowserCookies` adds to a message that is `browser: true` the `Cookie` header with what its device holds for the site it asks, and `rememberCookie` keeps the cookie of a `Set-Cookie` for the site that sent it (the same name and site replace each other). A message that is not from a browser (a `curl`) gets and keeps nothing: it carries a cookie only when the session wrote the `Cookie` header into it, which a `curl -b` does. The stage keeps the memory in `Carried.browser`; the card of the browser reads it with `browserAfter` (`../../simulation/sequence.ts`).
- The users of a site are `Site.accounts` (`../schema.ts`): `users` (`{ name, password, role }`), the `realm` and the bodies of the 401 and the 403. The engine writes no sentence: every body comes from the data of the app.
- Not here: the schema of a site (`../schema.ts`), the page and the response (`../app.ts`, `../messages.ts`), the Spanish text of why an app answered 401 or 403 (`src/copy/web/`).
