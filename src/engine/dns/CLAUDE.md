# engine/dns

Names and their answers: the zones an authoritative server holds, the records in them, and what a resolver says when a device asks it for a name. Pure functions over the network; the stage that calls them is `src/engine/simulation/stages/dns.ts`. The network model and its schema are in `src/engine/network/`.

- **The model (decided 13 and 14 of chapter 2).** A server of the internet (`ServerActor`) can carry `dns`: `role` `resolver` or `authoritative`, `upstreams` (for each zone, the authoritative server a resolver asks, by id), `zones` (each `{ name, records }`), `cache` (entries `{ name, type, value, expiresAt }`, the initial cache of the resolver: see *The cache*) and `failing`. A device of an office has `dnsServer`, the IP of its resolver (the one DHCP lent it, shown in the network settings), and may have `hosts`, the lines `{ name, ip }` of its hosts file (see *The hosts file*). A VPC has neither: its names are the EC2 ones (`src/engine/network/naming/`), resolved as before. The servers listen on port 53 of UDP and of TCP (RFC 1035 §4.2, read on 2026-10-11: name server access "using TCP on server port 53 (decimal) as well as datagram access using UDP on UDP port 53 (decimal)"; RFC 7766 §5, read the same day: "Authoritative server implementations MUST support TCP", and so must a recursive server), and every question of the game goes over UDP: the game never uses TCP for a question.
- **A record** is `{ name, type, value, ttl }`. `A` has an IPv4 as value, `CNAME` and `NS` a name and `SOA` the seven fields below. The player puts in and takes out only `A` and `CNAME` (`editableRecordSchema`, `recordKeySchema`): the `NS` and the `SOA` belong to the zone and `zoneOf(name, records)` puts them at its apex. Names are compared without case and without a trailing dot (`normalizeName`); a zone holds the names equal to it or below it (`isWithin`), and a server holding several zones answers from the one with the longest name (`zoneHolding`).
- **The CNAME rule** is one predicate, `holdsAliasAndMore`, that the network schema applies to every name of every zone and that `recordProblem` applies to the record a player adds. RFC 1034 §3.6.2: "If a CNAME RR is present at a node, no other data should be present"; RFC 2181 §10.1 makes it exact: a label has one CNAME, or records and none of them a CNAME (both read on 2026-10-11). The apex of every zone has NS and SOA, so no CNAME fits there. `recordProblem(net, serverId, record)` returns a code, never text (`RECORD_PROBLEMS`): `no-zone` (the server is not authoritative or holds no zone for the name), `already-there`, `name-is-an-alias` (an address next to an alias), `cname-with-other-records` and `cname-at-apex` (the case of the apex tells the view it can say that the zone has records of its own). `addRecord` applies a record only when there is no problem and otherwise returns the same network, so the view asks `recordProblem` first.
- **Every zone has exactly one SOA, at its apex**, and every record is within the zone (`networkSchema`). A resolver's `upstreams` name authoritative servers that exist, and a name server counts for the rule that no IP repeats.
- **The SOA of every zone is data, with fixed values** (`soaOf`). The seven fields are those of RFC 1035 §3.3.13 (MNAME, RNAME, SERIAL, REFRESH, RETRY, EXPIRE, MINIMUM, in that order) and each constant in `records.ts` carries its source and the date it was read, all on 2026-10-11:

  | Field | Value | Source |
  |-------|-------|--------|
  | TTL of the record | 300 | number of the game (decided 25), like the TTL of every record |
  | MNAME | `ns1.<zone>` | RFC 1035 §3.3.13 says what it is; the example zone of RFC 2308 §10 names its server `NS1.XX.EXAMPLE.`; the word `ns1` is the game's |
  | RNAME | `hostmaster.<zone>` | RFC 1912 §2.2 prefers "the generic name `hostmaster`" and says the `@` of the address is replaced by a `.`; the mailbox is fictitious |
  | SERIAL | 2026101101 | RFC 1912 §2.2 recommends YYYYMMDDnn; the date and the revision are numbers of the game |
  | REFRESH | 1800 | the example zone of RFC 2308 §10; inside the 20 minutes to 2 hours of RFC 1912 §2.2 |
  | RETRY | 900 | the example zone of RFC 2308 §10; RFC 1912 §2.2: "typically some fraction of the refresh interval" |
  | EXPIRE | 1209600 | the low end of the "2-4 weeks" of RFC 1912 §2.2, which asks it to be greater than the minimum and the retry intervals |
  | MINIMUM | 1200 | the example zone of RFC 2308 §10 |

  RFC 1912 is Informational, and the RFC Editor lists nothing that obsoletes it (`https://www.rfc-editor.org/rfc/rfc1912.json`, 2026-10-11): its values are "typical", not mandatory. **MINIMUM is greater than the TTL of the records on purpose.** RFC 1035 §3.3.13 gave MINIMUM another meaning, a lower bound on the TTL of every record of the zone; RFC 2308 §4 says that meaning "has never in practice been used and is hereby deprecated" and leaves MINIMUM as the TTL of negative answers. The game follows RFC 2308: no record is raised to MINIMUM, so do not "fix" the 1200 to match the 300. The game has no secondary server, so REFRESH, RETRY, EXPIRE and SERIAL are shown and never used. The NS record names `ns1.<zone>` and the zone has no address record for it, since the delegation from the parent zone is not modelled.
- **A negative answer carries the SOA, with the TTL of RFC 2308 §3** (`negativeAnswerSoa`, `negativeTtl`): "The TTL of this record is set from the minimum of the MINIMUM field of the SOA record and the TTL of the SOA itself" (§3, repeated in §5; read on 2026-10-11). The record in `Trace.dns.soa` is the zone's SOA with that TTL in place of its own, and its seven fields untouched. The game does not cache NXDOMAIN (decided 13), so the TTL is handed over whole; RFC 2308 describes how a real resolver would cache it. The tests build the zone both ways, TTL below MINIMUM and MINIMUM below TTL, because with the game's values (300 and 1200) only one branch runs.
- **What a resolver answers** (`answerFromUpstreams`). It asks the authoritative server of the longest zone that holds the name, by `upstreams`; the question and the answer are not packets of the map, and the chain root, top-level domain, authoritative does not exist. An `A` answers (`NOERROR`). A `CNAME` is followed, in the same zone or in another one, and the chain comes first in `answers`; the bound is `MAX_ALIAS_STEPS` (8 aliases followed), the game's own, and a loop of aliases or a chain longer than that ends as `SERVFAIL` (the game does not claim a real resolver stops at the same place). A server with `failing`, or one that holds no zone for the name (a lame delegation), gives `SERVFAIL` with no answers and no SOA. A name that no zone of the resolver holds gives `NXDOMAIN` with no SOA: with no root and no TLD the game has no zone to quote. A name that nobody holds a record for, below a zone that exists, gives `NXDOMAIN` with the SOA of the zone. A name that holds records but no address (the apex, with only NS and SOA), or only has names below it, gives `NOERROR` with no address and the SOA: RFC 2308 §2.2 (no data) and RFC 8020 §1 ("nonexistence of a node implies nonexistence of the entire subtree", so a name with names below it exists), read on 2026-10-11. An alias whose target does not exist gives `NXDOMAIN` with the alias in `answers` (RFC 2308 §2.1: the NXDOMAIN refers to the name at the end of the CNAME). The game has no `NODATA` status: the `NOERROR` with no `A` among the answers is it, and the stage ends the packet as `unresolved` with `dns-no-address`. So `Trace.dns.soa` can be on a `NOERROR` trace: its presence alone is no license to print an authority section in `dig` (see *Sin verificar*).
- **The question is a packet** (`resolve`). The device sends a UDP datagram to port 53 of `Device.dnsServer` through `send`, which the pipeline fills with `sendQuestion` (`simulate.ts`, a `run` of its own): so the question meets the firewalls of the device, its routes, the NAT of the office and the services of whoever is there, like any other datagram. It is answered when its trace is `replied` and the one reached is a server with `dns.role` `resolver`; then the resolver is asked for the name (`answerFrom`). Anything else is `NO-RESOLVER`, with the trace of the question in `Resolution.query`. The `dns` stage keeps the question it sent in `Trace.question` (see *The question of a lookup is a datagram of the send that asks*). A device with no `dnsServer` sends nothing and gets `NO-RESOLVER` too.
- **The reasons of a name that nobody answered.** Each reason has one meaning, and no case has two. The map, by what the question did:

  | What happened to the question | Reason of the step in the `ping` or `nc` | In a `dig` |
  |-------------------------------|------------------------------------------|-----------|
  | The device has no `dnsServer` (an office), or the EC2 name is unknown (a VPC) | `dns-unresolved`, pinned by chapter 1 | the same step |
  | It never reached a host: a firewall dropped it (`timeout`), a router dropped it or warned (Net or Host Unreachable, Time Exceeded), the sender warned that nobody has the IP, or there is no route | `dns-resolver-silent` (no resolver spoke) | no dns step; the trace is the trip, with its own steps and its `notice` |
  | It reached a host with no service on port 53, or one that listens only on another address: the host answers Port Unreachable | `dns-no-resolver`, with the `hostId` of that host | the `host-udp-closed` or `host-wrong-address` step of the host and a `notice` `port-unreachable` from it |
  | It reached a host that listens on port 53 and answered, and the host is no resolver (an authoritative server, any other program) | `dns-no-resolver`, with its `hostId` | `replied` with `dns.status` `NO-RESOLVER` |
  | It reached a resolver | `dns-answered`, `dns-cached`, `dns-nxdomain`, `dns-servfail` or `dns-no-address` | `replied`, the answer in `Trace.dns` |

  `Resolution.notAResolver` is the `hostId` of the third and fourth rows and is absent from the second. `dns-no-resolver` is only the case where a host got the question and did not answer it as a resolver (it is no resolver, nothing listens on port 53 there, or the resolver listens only on another address); `dns-resolver-silent` is only the case where no host got it. A `ping` by name does not carry the warning that came back (a Port Unreachable, a Host Unreachable) in its own trace: it is in the trace of its question (`Trace.question.trace.notice`) and, for a `dig`, in the trace itself.
- **The cache** (`cache.ts`). The cache is the resolver's: the question has to reach the resolver first, so a firewall that drops it keeps the answer out however full the cache is. A resolver answers from its cache when every record of the chain, from the name down to an address, is alive; a record is alive while `now` is below its `expiresAt` and gone at that very second, so a record stored at second `t` with a TTL of 300 answers until second `t + 299` and the resolver asks again at `t + 300` (RFC 1035 §4.1.3, read on 2026-10-11 at `https://www.rfc-editor.org/rfc/rfc1035.txt`: the TTL is "the time interval (in seconds) that the resource record may be cached before it should be discarded. Zero values are interpreted to mean that the RR can only be used for the transaction in progress, and should not be cached"; RFC 2181 §8, read the same day: "The TTL specifies a maximum time to live, not a mandatory time to live", so the game obeys the TTL it is given and a real resolver may cut it short). The records of a cached answer carry the seconds they have left, and `Trace.dns.ttlLeft` is the smallest of them, those of the record that expires first. If one link of a chain of aliases ran out, or the name asked is not in the cache whole, the resolver asks for the whole chain and stores every record of the answer, replacing the entries it had for those names, the initial ones included: asking for an alias (`blog`) whose target (`www`) has a live entry in the initial cache retires that entry with the answer of the authoritative server, and the next `dig www` gets the new address. The game models the answer of a chain as one answer. Whether a real resolver does the same was **not verified**, and it is an open choice for the incidents that offer an alias beside a stale cache (see *Sin verificar*). A resolver stores the records of an answer that holds an address, each until `at + ttl`, replacing what it had for that name and type; NXDOMAIN, SERVFAIL, a name with no address and a TTL of 0 are not stored (decided 13: the game does not cache NXDOMAIN). The initial `dns.cache` of a resolver (decided 24) is read beside what the sequence stored, against the same clock, and what the sequence stored for a name and type replaces the initial entries for it. The cache travels in `Carried` (`dnsCache`, by resolver id) from one send to the next; the clock is the `at` of each send, and `simulate` leaves at 0. Every answer of a resolver fills the cache, also the one a `ping` or an `nc` by name triggered, because a real resolver stores what it answers whoever asked; the question of a send by name does use a source port of the sender and does leave a row in the table (see below).
- **The hosts file** (`hosts.ts`). A lookup of the system (`lookup` `system`, what `ping` and `nc` do, the default of a packet) reads the hosts file of the device before it asks anybody, even when the device has no resolver: a line for the name answers it, `Trace.dns` is `{ status: 'NOERROR', answers: [], usedHostsFile: true }` (a line is no DNS record, so it has no TTL and the address is the `resolvedIp` of the trace), the step is `dns-hosts-file`, no question is sent and no resolver stores anything. A `dig` (`lookup` `dig`) reads no hosts file. Names are compared like DNS names (no case, no trailing dot); that the hosts lookup of a real system compares them the same way, that `getent hosts` or `ping` read the file before DNS on Amazon Linux, and that `dig` skips it there were **not verified here**: the order is the one of the plan (decided 2026-10-11; `dig` not reading hosts is marked local in the spec), and `src/copy/` quotes no system for it.
- **A `dig` is the datagram to the resolver** (`PacketSpec.lookup` `dig`). The `dns` stage does not look the name up before the trip: it points the packet at the resolver and the answer is taken when the trip ends (`answerFrom`, called from `conclude` in `simulate.ts`, with the finished trace as the question), so the trace of a `dig` is the trace of the datagram (see `src/engine/simulation/CLAUDE.md`). `answerFrom` is also what `resolve` calls after it sends the question of a lookup of the system, so both modes take the answer in the same place. The `dig` of a sequence uses a source port of its sender and leaves a row in the translation table, because it is a send of the player.
- **The tcpdump lines and the legs of the question are not merged into the trace of the packet that asked.** The question has a trace of its own, `Trace.question.trace`, so the tcpdump of a device that took the question (a device with a service on 53, which `ping` or `nc` by name never reaches while it is not a resolver) and the legs it crossed are in that trace and not in the one of the `ping` or the `nc`. Nothing reads `Trace.tcpdump` in the interface today; merging them would change what the player reads in a device's tcpdump, so it stays out.
- **The question of a lookup is a datagram of the send that asks** (O-2 = A, decided 2026-10-12). A `ping` or an `nc` (`lookup` `system`) of a device of an office that has a `dnsServer`, to a name the hosts file does not answer, puts one question before its packet, and the trace of the send carries it as `Trace.question`, `{ packet, trace }`: `packet` is the UDP datagram to port 53 of the resolver as it left, with its `sourcePort`, and `trace` is its whole trace (header with ports, `exchange` of query and answer, `translation` with its row, hops, warning), with `dns` the way a `dig` carries it (`viaDig` true: the answer of the resolver, `NO-RESOLVER` when nobody answered); the `dns` of the packet that asked keeps `viaDig` false. It exists in no other trace: not with an IP as destination, not when the hosts file answers, not when the device has no `dnsServer` (that is `dns-unresolved`), not in a `dig` (it is the question itself), not in a VPC, not in chapter 1 (nobody has a resolver) and not inside another question. The question runs through `sendQuestion` (`simulate.ts`) with the NAT table, the port counters and the second (`ctx.now`) of the send that asks, and hands the table and the counters back: it takes the next source port of the sender before the packet does (question 51514, `nc` 51515) and leaves its row before the packet does (question 40001, `nc` 40002), so a `ping` by name leaves the row of its question and none of its own. A `port` stage after `dns` gives the packet its port, which is why a send that ends before it (an address that is not valid, a name nobody resolved) takes none of its own: a real `ncat` leaves in `getaddrinfo`, before it opens a socket (`ncat/ncat_main.c` line 883, nmap 7.93). The question writes no step, reason, hop or leg in the trace of the packet that asked: its steps are the ones they were. The game asks again in every send and the resolver answers from its cache if it has the name (the cache still fills with every answer). The player's own `dig` is the datagram itself and does use its port and leave its row, as before. `lookup` modes: `system` (`ping`, `nc`) reads the hosts file and then asks the resolver, and `dig` is the question; they differ in `viaDig` of the trace, in the hosts file and in what the trace of the send is.
- **What the question of the game leaves out of a real one** (read on 2026-10-12; none of it is said on screen, because it would need IPv6, AAAA, reverse query and search domains, which are no terms of the game). The game draws one question, the one for the A record, and its answer. It is exact in what the player can check, the source port and the row of the NAT table, and it leaves out: (1) the AAAA question. `ping` (iputils `20211215`, `ping/ping.c` lines 556 to 558) and `ncat` (nmap 7.93, `ncat/ncat_core.c:102` and `ncat_main.c:883`) call `getaddrinfo` with the family unset and without `AI_ADDRCONFIG`, so glibc 2.39 (`resolv/nss_dns/dns-host.c`, `_nss_dns_gethostbyname4_r`, line 418) sends the A and the AAAA at once and `resolv.conf(5)` says they go in parallel, from the same socket (`single-request-reopen`: "The resolver uses the same socket for the A and AAAA requests"), so the NAT translates both with one row; (2) the reverse question (PTR) that `ping` makes without `-n` to name the IP that answers (`pr_addr`, `ping.c` lines 1625 to 1643; `ncat` uses `getnameinfo` only with `NI_NUMERICHOST`); (3) the search domains a real resolver tries when the name does not exist (`search` and `ndots` of `resolv.conf(5)`); (4) the retries when nobody answers (`timeout` 5 s and `attempts` 2 by default, `resolv.conf(5)`). A `dig` sends one question, of type A by default (`make_empty_lookup` of BIND 9.18.50, `bin/dig/dighost.c` lines 617 and 618): that is why a `dig` is already the question the game draws.
- **The order of the hosts file and the DNS, and the cache of the machine.** glibc 2.39 has `hosts: files dns` as the default of `nss/nss_database.c` (lines 83, 98 and 135 to 137), `nsswitch.conf(5)` says the services are queried in the order of the line until a result is found, and the Fedora `sssd` profile of `authselect` also puts `files` first, so `ping` and `nc` read the hosts file first. `dig` never reads it (no reference to `/etc/hosts` in `bin/dig`, `lib/isc` or `lib/dns` of BIND 9.18.50, and `dighost.c` reads `resolv.conf`, lines 1277 and 1327). Every `ping` and every `nc` is a process that resolves once (`ncat_main.c:883`, `ping.c:558`), and glibc keeps no cache of its own; `nscd(8)` and `systemd-resolved(8)` do, so a machine that runs one may not send a second question inside the TTL. The game does not model that cache: it asks again in every send, and the one that keeps the answer is the resolver.
- **Sin verificar.** What a real resolver does with a live cached address when it asks for an alias of that name and the answer brings a different address for it (retire the cached one, as the game does, or keep it until it expires) was not checked against a source; `cache.test.ts` states what the game does. What the `dig` of BIND 9.18 prints is in `src/copy/tools/CLAUDE.md`, with its sources: `dig` prints a section only when the reply has records in it, and the resolver of the game puts the SOA only in a negative answer (an NXDOMAIN or a name with no address) and nothing else in the authority section; what a real server adds there (NS records, glue) was not checked. Whether a real resolver gives `SERVFAIL` for a lame delegation and for a loop of aliases was not verified against a source; the game does it because it has no better answer to give. Not verified about the question of a send by name (read on 2026-10-12): what Amazon Linux does (its `/etc/nsswitch.conf`, and the versions of `iputils`, `glibc` and `nmap-ncat`; the pages of AL2023 consulted do not carry them), that the `ping` and the `nc` of the player are the versions read (`main()` and `pr_addr` may differ in others), that a hosts line with only an IPv4 address ends the lookup in `files` and sends not even the AAAA (reasoned from the `success` → `return` rule of `nsswitch.conf(5)`, `nss_files` not read), and the cache of the machine in AL2023 (one report of a user on AWS re:Post, not an official source: `systemd-resolved` with the stub listener off by default).
