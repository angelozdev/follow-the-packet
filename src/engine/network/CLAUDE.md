# engine/network

The network model as zod schemas and types: an office or a VPC (`kind`), its range, its devices (laptop, printer, EC2 instance), its firewalls (host firewall or Security Group), its edge (router or Internet gateway) and the actors on the internet. An office can also have floors (LANs) and routers. Also actions that change a network. CIDR math (the private ranges of RFC 1918, the loopback range of RFC 1122), the topology questions and the questions a router asks of the model live in `addressing/`. EC2 DNS names and app targets live in `naming/`. What listens on a device or a server and on which address lives in `services.ts`.

- `networkSchema` checks each kind: a VPC has a region, subnets, a Security Group on every device and an Internet gateway as its edge, and declares no LANs and no routers; an office has no region, no subnets and no public IPs, and its edge is a router. Both kinds use a private range (RFC 1918).
- An office has one LAN, the one of its `cidr`, unless it lists `lans` (floors, each with its range and the `latencyMs` of a hop). A device says its LAN with `lanId`, which it can leave out only while the office has one LAN, and sits inside that LAN's range. `lansOf` and `lanOf` (`addressing/topology.ts`) answer both questions, and `isConnected` says whether a device has its cable. A LAN's range is a detail of the model and the game never shows it.
- A device can also carry a default `gateway` (an IPv4 address) and `connected: false`, which is a device with no cable: it neither sends nor receives.
- `routers` lists the routers of the office and of the road to the internet. A router has `interfaces` (`ip` and `faces`, the id of a LAN, another router or a server), `routes` (`to` is a range or `default`, `next` the id of a router), the `latencyMs` of a hop and `sendsUnreachable`, which says whether it warns when it has no route or stays silent. A router holds one route to each destination: `sameDestination(a, b)` (`schema.ts`) says two destinations are the same when they are the same range, written by its first address and prefix (`198.51.100.7/24` is `198.51.100.0/24`), and `default` is `0.0.0.0/0`, so `networkSchema` rejects a table with two routes to the same one (`router-office: two routes to default`). The rule covers the routes a router stores, not the rows the routing table derives (a connected row and a stored route to the same range can both exist). Routes are given by the world; the player never edits them in chapter 1.
- A router can carry `forwards`, its port forwards: each is `{ protocol: 'tcp' | 'udp', publicPort, toDeviceId, toPort }`, a fixed translation that sends what comes from outside to the public IP of the router, on that protocol and port, to a device of the office and to the port its program listens on (`src/engine/nat/CLAUDE.md`). Both ports go from 1 to 65535. `networkSchema` rejects a forward whose `toDeviceId` is not a device (`router-office: the forward of tcp 8080 goes to ghost-laptop, which is not a device`); a VPC has no routers, so it has none. The field is absent from a router with none, so a router is the same one as before. Nothing else about a forward is checked: the schema neither rejects two forwards for the same protocol and port (the first one wins) nor asks that the device be on a LAN the router faces.
- A server of the internet can carry `dns`: `role` (`resolver` or `authoritative`), `upstreams` (`{ zone, serverId }`), `zones` (`{ name, records }`), `cache` and `failing`; a device of an office can carry `dnsServer`, its resolver, and `hosts`, the lines `{ name, ip }` of its hosts file. A record is `A`, `CNAME`, `NS` or `SOA` (the SOA is an object with the seven fields of RFC 1035 §3.3.13; TTLs go from 0 to 2^31 - 1, RFC 2181 §8). The schema asks that every zone have exactly one SOA, at its apex, that every record be within its zone, that no name hold a CNAME and another record, that each `upstreams.serverId` be an authoritative server that exists, and that a VPC have no `dns`, no `dnsServer` and no `hosts`. The rules and the SOA values are in `src/engine/dns/CLAUDE.md`. The actions: `setDns` (replaces the `dns` of a server of the internet; with none, the field goes away), `setDnsServer` (`server`, like `setGateway`: with none, the device has no resolver), `setHosts` (replaces the hosts file of a device; with no line the field goes away, like `setForwards`), `addRecord` and `removeRecord` (an `A` or a `CNAME` of a zone of an authoritative server; they return the same network when there is no such server or zone, when `recordProblem` says the record does not fit, or, for `removeRecord`, when the zone has no record with that name, type and value).
- No IP repeats among devices, router interfaces and servers. Every interface faces a LAN, a router or a server that exists, every route goes through a router that exists, and a LAN, a router and any other id never share a name.
- The questions a router asks about the model (`interfaceTowards`, `ownsIp`, `facesALan`, `bestRoute` and `onwardFrom`) are answered in `addressing/routing.ts`.
- An actor of kind `server` is a server of the internet: it answers Echo Request, accepts a TCP connection or a UDP datagram on the ports of its `services` (none unless it lists them), has no firewall and carries its `latencyMs`. It is not an actor of the map (`ClientActor` is every other actor, and `isClientActor` tells them apart).
- A `Service` is `{ protocol: 'tcp' | 'udp', port, listen: 'all' | 'loopback' }`: a program that listens. `port` goes from 1 to 65535 (IANA marks 0 as reserved). A device lists its services in `host.services` (always present; `[]` for a device with no program) and a server of the internet in its optional `services`. `host.services` replaced `host.listeningTcpPorts`, which was TCP only and had no address. `lookupService(services, protocol, port, destinationIp)` (`services.ts`) answers `accepts` (a service of that protocol and port listens on the destination IP), `wrong-address` (one listens on that protocol and port, but not on that IP) or `closed` (none does). `listensOn(service, ip)` is the rule: `all` takes a packet whatever its destination IP, because the packet reached the device by one of its own IPs (a `127.x.x.x` included), and `loopback` listens on `127.0.0.1` only (`LOOPBACK_IP`), so it takes a packet to that exact address and refuses one to any other IP of the device, another `127.x.x.x` address included (decided 2026-10-11). A packet to a `127.x.x.x` address reaches a device only when that device sends it to itself, because the route stage delivers any address of the loopback range (RFC 1122 §3.2.1.3) to the sender.
- **Sin verificar (2026-10-11).** That the listening address decides by the destination IP of the packet (decided item 8 of `docs/plans/2026-10-11-follow-the-packet-chapter-2.md`) is reasoned from `ip(7)` ("bound to all local interfaces" for `INADDR_ANY`), not tested on a real machine. So a service on the loopback address answers a packet to the IP of the network of its own device with a reset (TCP) or a Port Unreachable (UDP), also when the device sends it itself. The same holds for a packet to another `127.x.x.x` address, which a service bound to `127.0.0.1` refuses too. The student can test both on an EC2 (a service bound to `127.0.0.1` and an `nc` from another machine, from the same machine to its network IP and from the same machine to `127.0.0.2`); if the real behavior differs, change `listensOn`, this note and the decided item, and write the result here. Until then no text of the game states it as a fact beyond what the trace shows.
- A `PacketSpec` can carry a `ttl`, an integer from 1 to 255; `DEFAULT_TTL` (64) is the one it leaves with otherwise. It can also carry a `sourcePort`, an integer from 1 to 65535 (IANA marks port 0 as reserved; the `port` a packet is for still allows 0, as before); `DEFAULT_SOURCE_PORT` (51514) is the one a TCP or UDP packet leaves with otherwise. ICMP has no ports. A packet for a name can say how the name is looked up with `lookup`: `system` (the default, what `ping` and `nc` do: the hosts file of the device first, then its resolver) or `dig` (the question itself: a UDP datagram to port 53 that reads no hosts file, which the schema asks of every `dig`); see `src/engine/dns/CLAUDE.md`.
- An action changes a network: it adds or removes a rule (`addRule` and `removeRule` take a `direction`, `inbound` or `outbound`; without it the action works on the inbound list, and `removeRule` only looks in the list of its direction; `DEFAULT_DIRECTION` is the direction of an action that gives none), sets an app target, the host's echo setting or a gateway, plugs a device in, adds an actor on the internet, a firewall (which it puts on its device), a LAN, a device or a router, or replaces the services of a device or of a server of the internet (`setServices`, with its `ownerId`) or changes the listening address of one of them (`setListenAddress`, with `ownerId`, `protocol`, `port` and the new `listen`: it changes the one service with that protocol and port and keeps the rest), or replaces the port forwards of a router (`setForwards`, with its `routerId` and the new list: an empty list takes the field away, so a router that had none is the same one as before, and `changedNames` does not see a change that is not one), or replaces the routes, the interfaces or the unreachable behavior of a router (a router that must face one added after it, such as the uplink of the office router to the first router of the provider, gets its interfaces replaced then), or edits one route of a router: `addRoute` (`routerId`, `route`) adds it at the end of the table, and `removeRoute` (`routerId`, `to`) removes the route of that destination and keeps the rest. Neither checks that the next hop is a router: like `updateRouter`, the schema does. An action that names something the network does not have returns the same network: an owner that is no device and no server of the internet (a client actor included), a `setListenAddress` for a protocol and port the owner does not serve, a router that does not exist, an `addRoute` for a destination the router already has a route to (whatever its next hop, however the destination is written) and a `removeRoute` for a destination it has none to. `routeProblem(net, routerId, route)` says why an `addRoute` is rejected, as a code and never as text (`ROUTE_PROBLEMS`: `no-router`, `destination-has-route`), the way `recordProblem` does for a record; `addRoute` applies a route only when it returns undefined, so the view asks it before the action.

- A TCP `Service` can carry `web`, what it answers when someone speaks HTTP to it: its sites and the default site (`src/engine/web/CLAUDE.md`); a service without it accepts the connection and says nothing. `networkSchema` rejects a `web` on a UDP service. A `PacketSpec` can carry a `message`, the HTTP request a client makes (`method`, an absolute `url`, `headers`, `body`), and only in a TCP packet: `packetSchema` rejects it in UDP and ICMP.
- A device can carry `host.processes`, the programs that run on it (`{ id, name, running }`), and a `Service` can name one with `processId`: a service of a process that is not running does not listen, so the port is closed (`lookupService` answers `stopped` instead of `closed`, with the processes of the device as its fifth argument, and the host stage writes `process-stopped`; a service with no `processId` listens as before). `networkSchema` asks that a `processId` be a process of the device it is on (a server of the internet has no processes, so none of its services can name one) and that a VPC have neither `processes` nor a web service. The action `setProcess` (`deviceId`, `processId`, `running`) sets whether a process runs and keeps the rest; it returns the same network when the device or the process is not there. The action `addSite` (`ownerId`, `port`, `site`) adds a site to the web service of a device or a server of the internet on that TCP port, at the end of its list; `siteProblem(net, ownerId, port, site)` says why it does not (`SITE_PROBLEMS`: `no-web-service` when the owner has no web service on that port, `name-has-site` when a name of the site, compared as DNS names, is already the name of a site of the service) and `addSite` returns the same network exactly then. The names of a site go under `.example` (`src/engine/web/CLAUDE.md`). No server of the internet gains a process: the block does not need one.
