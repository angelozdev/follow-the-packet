# engine/nat

The NAT of the office: what it does with the source of a packet that leaves, and the table it keeps while a sequence of packets goes on. Pure functions over a table that arrives as an argument and leaves as a result; the stage that calls them is `src/engine/simulation/stages/nat.ts`.

- The NAT is not configured and is not stored in the network: it is derived from the topology (decided 3 of chapter 2). A router that faces a LAN (`facesALan`) and sends a packet out through an interface with an IP that is not private (RFC 1918) translates the source of a packet that a device of the office sent (`publicIpOf`, whose answer is that interface's IP). In the worlds of chapter 1 that is `router-oficina`, whose uplink `203.0.113.10` already existed. The link to another office has a private IP, so it translates nothing. There is no field in `Network` and no action to turn it on: chapter 1 already showed a ping from `192.168.1.10` reaching `198.51.100.50`, and a world that switched the NAT on later would have shown traffic that could not exist.
- A translation (`Translation`) is `{ protocol, inside, outside, isNew, fixed }`: the end the device sent from, the end the packet leaves the office with, whether this packet made the row and whether the row is a fixed one (a port forward, which task 11 adds; it is always `false` today). It is `Trace.translation`, a field of its own: the NAT writes no step, reason, hop or leg, and the header (`Trace.header`) and `effectiveSource` keep the private IP, because that is what the sender sent. The view reads the field to show the header outside the office.
- The table (`NatTable`) is a list of rows `{ protocol, inside, outside }` that `translateSource` extends and never changes in place. TCP and UDP make a row; ICMP does not. A ping is translated to the public IP with no ports (an Echo carries an identifier and a sequence number, and it is the identifier that a real NAT translates, RFC 792 and RFC 3022 §2; the game hides it) and leaves no row.
- The mapping is independent of the destination: the same private IP and port reuse their row towards any server, for TCP (RFC 5382 REQ-1, read on 2026-10-11) and for UDP (RFC 4787 REQ-1, read on 2026-10-11). A different protocol, private IP or private port is another row.
- The numbers are the game's, not any system's: public ports start at `FIRST_PUBLIC_PORT` (40001) and each new row takes the next free one, whatever its protocol, so the rows of a sequence are 40001, 40002, 40003 in the order the packets left. The source port is not kept (the example of RFC 3022 §2 changes it too: `10.0.0.10:3017` becomes `138.76.28.4:1024`). A row has no time to live and the table has no limit, so no port is ever reused or runs out. Other NAT choose other numbers, and a real one expires its rows.
- A row exists from the moment a packet leaves through the router, even if the packet dies later on the road: the translation is made where the packet goes out, not where it ends. A packet the router discards for its TTL, or that finds no route there, was never sent out and makes none.
- A loose `simulate(net, packet)` knows nothing of the sends before it, so it translates against an empty table: the same packet always gets 40001. `simulateSequence` carries the table from one send to the next (`src/engine/simulation/CLAUDE.md`).
- Not here: the pipeline and the context (`src/engine/simulation/`), the network model (`src/engine/network/`), the text the player reads (`src/copy/`).
