# game/view/cards/web

What the web adds to the views, computed from the session: the strip of the url of a terminal (`url-strip.ts`), the browser of an origin (`browser-card.ts`), the «Sitios» card of a web server (`sites-card.ts`) and the fields of the inspection box that tell a request (`web-fields.ts`). It is a folder of its own because `src/game/view/` and `src/game/view/cards/` are at their cap of files.

- The browser is a program of the device, not a piece of the map. `browserCard(session, pieceId)` is its tab for the piece of an origin whose incident offers a message with the command `browser` that opens an address (the one with no `signIn`): the origin and message chips to send with (`fromId`, `messageId`), an address chip for each url, labelled by the whole url, `users` (one for each browser message that signs in, `{ messageId, label }`, in the order the incident offers them; none when it offers no sign-in) and `remembered`, the cookies its device holds since the world last changed (`{ id, site, name, value }`, from `browserAfter` of the engine over `replayOf(session.history)`, the replay the cache card uses), or null while the term `cookie` is unknown. Signing in is a send like opening: the player picks an address and a user and the tab sends the message of that user to that address, which makes a `POST` to the login of the site of the address with the form of the user; the player types nothing. `browserView(session, picks)` is what it shows for an address already opened or signed in to since the world last changed, the latest of the two for that origin and address: the url the browser went to (the login for a sign-in), and the page (the lines of the body of the response, the 404 and the 401 included) or an error in the game's own plain words (`BROWSER_TEXT`: «La conexión se rechazó» for a refusal, «No se pudo conectar» for a silence or any other result with no response, and a third text for a service that accepted and sent no page). It imitates no real browser and names no error code or status code. The browser of the game does not open the box for the user and the password that a real one opens before a 401 with `WWW-Authenticate`: the player signs in by the tray «Usuario» and the button, and the box of a 401 for the browser says so (`WEB_BOX_TEXT.browserLoginBox`). The terminal does not offer the `browser` message (it has no command line); `pieceCard` lists the tab «Navegador» right after the terminal, and `src/ui/incident/map-cards/web/browser-card.tsx` draws it.
- `urlStrip(chips)` is the strip of the url (V28 = B) of the address chips of a send: a tray for each part of the url (scheme, name, port, path, query string), in the order of the url, with the values the chips give, and the address chip each combination of values stands for. It is null unless there are several chips and every one gives its url by parts (a chip that gives its whole url, or that is no url, keeps the tray of whole addresses: from 03-02 the urls come whole). `terminalCard` carries it as `strip` and then has no tray of addresses; `pickedParts` gives the picks with the part that offers a single value already picked, and `stripAddress` the id of the chip whose url the picks write (undefined while a part is missing, or when the chips do not make that combination, so an incident that gives its urls by parts gives every combination of its values).
- `sitesCard(session, pieceId)` is a `TableCard` of kind `sites` for the owner of a table of sites: a row for each site of the web service on the port of the table, with the names it answers to (the default site marked, and a default site with no name answers to any name) and what it serves, in the words of the chip whose content it is or, when none is, the body of its only page when that page is fixed and otherwise the paths of its pages. The player only adds sites: no row has `entryId`. The trays are `name` and `serves`, the same names `placeEntry` takes. A refusal of the engine (`Session.entryProblem`) is the `problem` of the card, in the words of `SITE_PROBLEM_TEXT`.
- `web-fields.ts` gives the box of a packet that carries a message its fields, each behind its term and in this order: «URL» (`url`) in its parts right after what the packet is (scheme, name or IP, port and the default port of the scheme when the url wrote none, path, query string), «Petición HTTP» (`http-request`) and «Respuesta HTTP» (`http-response`) after the handshake as the request and the response travelled (start line, headers and a «Cuerpo» line), «Código de estado» (`status-code`) and «Quién lo generó» (`status-code`) right after the response (`statusCodeFields`: the code of the response with the term that names it and its class, plus, for a 401 or a 403, the sentence of the step `web-needs-login` or `web-forbidden` (`describeReason`) as a third line, and the device whose app answered, read from the step `web-answered` of the trace; a packet that got no response shows neither), and «curl» (`curl`) after the result when a `curl` waited and gave up (code 28, with the seconds of its `--connect-timeout`). The request is shown only when the connection opened (the trace has the ACK of the greeting): a refusal or a silence never sent it. The headers of a request are the engine's: a `curl` sends `Host`, `User-Agent`, `Accept` and, with `-d`, `Content-Length` and `Content-Type`, and with `-u` an `Authorization: Basic` between `Host` and `User-Agent` (the session adds all but `Host`, see `src/game/CLAUDE.md`); the response of a 401 shows its `WWW-Authenticate` among the headers, and the code of the 401 and of the 403 shows behind its own term (`status-401`, `status-403`) with the class line of the 4xx; the browser of the game sends only `Host`, plus the `Cookie` of what its device holds for the site and, when it signs in, the `Content-Length` and the `Content-Type` of the form, and the box says so («El del juego manda solo esta.» when it sent only `Host`, «solo estas.» when it sent more). The response note says a real server sends more headers, and a 401 for the browser adds that a real browser opens a box for the user and the password and the one of the game does not. A `Set-Cookie` of a response and the `Cookie` of a request are headers like the others: the box lists them as they travelled.
- The lines of the request and the response are the protocol's own text, the exception declared in rule 3 of the chapter 3 spec: they appear before `http-header` and `status-code` are taught. The two fields of `status-code` do not: they wait for the term.
- Not here: the terminal and what a `curl` prints (`cards/terminal/`), the other tables (`cards/table-card.ts`), the box itself (`src/game/view/inspection.ts`), the Spanish text (`src/copy/web/`), drawing (`src/ui/`).
