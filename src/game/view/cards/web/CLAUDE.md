# game/view/cards/web

What the web adds to the views, computed from the session: the strip of the url of a terminal (`url-strip.ts`), the browser of an origin (`browser-card.ts`), the «Sitios» card of a web server (`sites-card.ts`) and the fields of the inspection box that tell a request (`web-fields.ts`). It is a folder of its own because `src/game/view/` and `src/game/view/cards/` are at their cap of files.

- The browser is a program of the device, not a piece of the map. `browserCard(session, pieceId)` is its tab for the piece of an origin whose incident offers a message with the command `browser`: the origin and message chips to send with (`fromId`, `messageId`) and an address chip for each url, labelled by the whole url. `browserView(session, picks)` is what it shows for an address already opened since the world last changed: the page (the lines of the body of the response, the 404 included) or an error in the game's own plain words (`BROWSER_TEXT`: «La conexión se rechazó» for a refusal, «No se pudo conectar» for a silence or any other result with no response, and a third text for a service that accepted and sent no page). It imitates no real browser and names no error code or status code, and says nothing of cookies, redirections or HSTS: the browser of block 1 differs from `curl` only in showing the page. The terminal does not offer the `browser` message (it has no command line); `pieceCard` lists the tab «Navegador» right after the terminal, and `src/ui/incident/map-cards/web/browser-card.tsx` draws it.
- `urlStrip(chips)` is the strip of the url (V28 = B) of the address chips of a send: a tray for each part of the url (scheme, name, port, path, query string), in the order of the url, with the values the chips give, and the address chip each combination of values stands for. It is null unless there are several chips and every one gives its url by parts (a chip that gives its whole url, or that is no url, keeps the tray of whole addresses: from 03-02 the urls come whole). `terminalCard` carries it as `strip` and then has no tray of addresses; `pickedParts` gives the picks with the part that offers a single value already picked, and `stripAddress` the id of the chip whose url the picks write (undefined while a part is missing, or when the chips do not make that combination, so an incident that gives its urls by parts gives every combination of its values).
- `sitesCard(session, pieceId)` is a `TableCard` of kind `sites` for the owner of a table of sites: a row for each site of the web service on the port of the table, with the names it answers to (the default site marked, and a default site with no name answers to any name) and what it serves, in the words of the chip whose content it is or, when none is, the body of its only page when that page is fixed and otherwise the paths of its pages. The player only adds sites: no row has `entryId`. The trays are `name` and `serves`, the same names `placeEntry` takes. A refusal of the engine (`Session.entryProblem`) is the `problem` of the card, in the words of `SITE_PROBLEM_TEXT`.
- `web-fields.ts` gives the box of a packet that carries a message its fields, each behind its term and in this order: «URL» (`url`) in its parts right after what the packet is (scheme, name or IP, port and the default port of the scheme when the url wrote none, path, query string), «Petición HTTP» (`http-request`) and «Respuesta HTTP» (`http-response`) after the handshake as the request and the response travelled (start line, headers and a «Cuerpo» line), and «curl» (`curl`) after the result when a `curl` waited and gave up (code 28, with the seconds of its `--connect-timeout`). The request is shown only when the connection opened (the trace has the ACK of the greeting): a refusal or a silence never sent it. The headers of a request are the engine's: a `curl` sends `Host`, `User-Agent`, `Accept` and, with `-d`, `Content-Length` and `Content-Type` (the session adds the last three, see `src/game/CLAUDE.md`); the browser of the game sends only `Host` and the box says so. The response note says a real server sends more headers.
- The lines of the request and the response are the protocol's own text, the exception declared in rule 3 of the chapter 3 spec: they appear before `http-header` and `status-code` are taught.
- Not here: the terminal and what a `curl` prints (`cards/terminal/`), the other tables (`cards/table-card.ts`), the box itself (`src/game/view/inspection.ts`), the Spanish text (`src/copy/web/`), drawing (`src/ui/`).
