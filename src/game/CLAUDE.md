# game

The session of one incident, as a pure reducer: the current world, the run of every flow, the packets the player sent (the last one of each combination of chips, with the number of its send, and every send since the world last changed, in order, with the second of the game clock it left at), the game clock, the tasks (done or not, read from the runs and the sent packets at once), the sent solution and Lucía's reply, hints, the explanation and the stars. The middle star depends on the mechanic: only what is needed for a filter, no hints for a send or an identify, no hint in any case for a diagnose. What the map and the panels show lives in `view/`.

- Every run (a flow or a sent packet) carries `by`: the ids of whoever answered, warned or dropped the packet (a device, a router or an actor; for a packet a firewall dropped, the ids of the firewalls of that device; for a local error such as `no-route`, the sender; none when the network lost it). A send task holds when the outcome of the trace is the expected one and, if it names `by`, that id is among them; and, if it says what the DNS answered (`expect.answer`, `expect.status`), the trace of the send of its chips it looks at agrees (`dnsHolds`, `tasks.ts`), and, if it names a `body`, the response of the web service of that send has exactly that body, and, if it names a `statusCode`, that response has that status code (a message that got no response has neither). The send it looks at is the last of its chips or, when it says `nth`, the nth since the world last changed, so `taskHolds` and `failingTaskIds` take `Session.history` (every send, in order), not `Session.sent`; a later send does not undo a task about the nth.
- What a run shows depends on what the player knows (`Session.known`, passed to `runFlows` and `sendPacket`): `blocked` is true only when the firewall that dropped the packet is a known term. When it is not, the run is `hiddenStop` and `blocked` is false, so the packet leaves the lost stamp and ends at the door of its device. A packet with ports (TCP and UDP of an office) carries its labels for the map as `ports`: the label of each leg of its path and the router where they change, from `packetPortLabels` and the first router the packet crossed that faces a local network (`translatingRouter`); a run with no ports (a ping, any packet of a VPC) has no such key. A warning that came back (`Trace.notice`) is part of the run as `warning`, with the term that names it and who generated it (`router`, or `sender` when the sender's own device did): it is left out while its term is unknown, and the packet is seen as one that nobody answered. A warning with no term (`term` is null: a router with no route until `net-unreachable` is known) is kept once the first warning term (`FIRST_WARNING_TERM`, `host-unreachable`) is known and left out before, like any warning: giving a warning its right name must not change when it appears, and a player who has not met a warning yet is not shown one without being told what it is. Nothing else changes: the outcome, `reached`, `replied` and `by` are those of the trace, because the tasks read them.
- In a send incident whose routers wait for a traceroute (`revealsRoutersByTraceroute`), a packet that is not a traceroute and that a router dropped without a warning is also `hiddenStop`, before and after a traceroute has named the routers (`revealedRouterIds`, `view/revealed-routers.ts`, only decides which router pieces are drawn): a ping alone never reveals where it died, and a traceroute only says the break is very probably after the last router that answered, so the packet leaves and stops just outside its device with the lost stamp and never moves. `sessionReducer` and `startSession` set it on every run after each action (`hideStopsOutOfSight`, `src/game/flow-runs.ts`); nothing else about the run changes.
- A traceroute sent from a terminal is one entry of the sent packets: the run of the last probe it sent (the one that ended it), with all its probes in `route`. A single packet has no `route`. What the terminal prints for it is `tracerouteLines` (`view/cards/terminal/`).
- In an identify incident the session holds `answers`: the chip confirmed for each tray of each device (`answers[deviceId][trayId]`). It starts with the `initialPick` of every tray that has one, so starting the incident again puts them back, and a starting pick completes no task by itself; an item of the card that classifies (`identify.classify`) has no answer until the player places it. The action `answerCard` (`{ deviceId, picks }`, `picks` by tray id) saves the picks the card confirms; a card, a tray or a chip the incident does not offer is left out (the bins of the card that classifies are offered for each of its items, under the tray the card names, besides the trays of the card of the device itself), an answer that changes nothing returns the same session, and a change takes Lucía's reply away. An identify task holds when the confirmed chip for its device and tray is the one it expects (`taskHolds` and `failingTaskIds` take `answers` as their last argument). A pick only counts once the card confirms it: the draft before that is the card's own state (`src/ui/`), never the session's.
- A rule move (`placeRule` and `removeRule`) works on one direction of a firewall (in a send incident, the rules card of `send.rules` offers only the inbound ones, for its own firewall; a move that changes the world there clears the sends like any other: `move` ends in `withNewWorld`) (`direction`, inbound by default). `canConfigure(session, firewallId, direction?)` asks the ladder (`Session.parts.inboundRules` and `outboundRules`, per kind of firewall) for that direction, or for either one when none is given (a piece is configurable if any direction is). A rule placed in the other direction than the one the flow needs changes the world and leaves the runs as they were: a host firewall with its outbound side closed keeps stopping the ping after an inbound rule.
- A packet is not simulated on its own. `Session.history` holds every send since the world last changed, in order (`SentPacket`, each with its `send` number and its `at`, the second of the game clock it left at), and `Session.sent` is the last of each combination of chips, in the order of the first send of each (`lastOfEach`); the orders of an app (`Carried.apps`) live in that replay, so a move that clears the history clears them too. A new send simulates the whole history again with `sendSequence` (`flow-runs.ts`), which builds each packet with `sentPacketFromChips` (a `curl` carries the headers the real tool adds to its request) and hands the single packets to the engine's `simulateSequence`: what one send leaves behind (the source port of its device, the rows of the translation table, what the resolver remembered) is the input of the next, and each is measured against its own `at`, so the same sends always give the same runs and a send never changes an earlier one. The send number (`Session.sends`) goes on counting for the whole incident. A send by name puts its question first (O-2 = A): `SentPacket.question` is the run of that datagram to the resolver, built like the run of any packet (id `<send>-question`, its own stamp, box, labels with ports and warning, and `hideStopsOutOfSight` looks at it too), and `drawnSends(sent)` gives the list the map draws, each question before its packet and the packet with `after` set to the id of its question; only the last send of each combination is in `Session.sent`, so only its question is on the map, while the question of every send keeps its row in the history. A traceroute stays out of the sequence (it sends no TCP or UDP packet and asks no resolver, so it uses no port and leaves no row, and has no question run), and `sendPacket` is still the run of one send on its own, at second 0.
- The game clock (`Session.clock`, seconds, from 0) is the only time the game has: it moves only with the action `wait` (`{ seconds }`), which takes one of the steps of the incident's clock (`send.clock`) and nothing else, while the incident is open; a time that is no step, an incident with no clock and a diagnose change nothing. A wait keeps the world, the runs, the sends and Lucía's reply: only the `at` of the sends that come after it changes, and with it what the resolver's cache still holds. The clock never goes back.
- In a send incident the player also changes the world from the cards of its pieces, with three actions that share one rule (`edit`): `setSetting` (`{ deviceId, settingId, chipId }`) sets what the kind of the setting says (the default gateway, the DNS server, or the listen address of the service it names), `placeEntry` (`{ tableId, picks }`, one chip picked in each tray of a table) places a route in the table of a router, a record in the zone of a server of names or a site in the web service of a server (a table of `sites`, which the player only adds to), and `removeEntry` (`{ tableId, entryId }`) removes the row that has that id. A move that changes the world runs the flows again and clears `sent` and `history`, because the stamps of the packets sent before described the old world, and with them go the translation table and the cache that came from them; the clock stays, the send number goes on counting, Lucía's reply goes away, and the first TCP or UDP packet sent afterwards leaves from the first source port again. When the sends it clears were not empty, the session keeps what the move edited in `Session.restart` (`{ kind, ownerId }`, from `editedPart` in `src/levels/world.ts`: the kind of the setting or of the table, or a rule, and the device, router or server that holds it) and `restartNotice(session)` says it in words (`RESTART_TEXT`, `src/copy/screens/incident-ui.ts`): “Cambiaste cómo escucha la app de laptop-lucia: las pruebas de antes eran con la red anterior. Vuelve a mandarlas.” The card of the tasks (Lucía's, and the card of a case with a fix) shows it as a note until the player sends again; an edit that clears nothing leaves the notice as it was, and a filter, identify or diagnose case with no sends never has one. The ticks going away is intended (decided 5), the notice is what tells the player why. A chip already in effect, one the incident does not offer, a table it does not have, a row that is not there or an incident that is not a send return the same session. A closed incident changes nothing.
- When the engine does not take an entry the incident offers, `placeEntry` leaves the world, the sends and the clock as they were and keeps the reason in `Session.entryProblem` (`{ tableId, code }`): `code` is the engine's code, never text, a `recordProblem` code for a record (the CNAME rule, a record already there) or a `routeProblem` code for a route (a destination that already has one), found by `placementProblem` (`src/levels/world.ts`; a site gives a `siteProblem` code, `no-web-service` or `name-has-site`, whose sentence is `SITE_PROBLEM_TEXT` in `src/copy/web/`). The view says it in words under the table (`src/copy/`). It stays through a send, a wait and a hint and goes with the next entry or change of the world; the same refusal twice returns the same session. An entry the incident does not offer (an unknown table, a tray with no pick, a pick that is no chip of its tray) keeps no reason, because there is nothing to explain. Chips that make no entry although every tray has a pick do keep one: an address record whose value is no IP (`chipProblem`, `a-record-needs-ip`: an A record holds an IPv4 address, RFC 1035 §3.4.1), which the engine never sees because `placementOf` makes no record of it. The wait steps of the clock come from `clockSteps(session)`, which the `wait` action and the clock card of the screen share.
- In a diagnose incident the session is on one case at a time (`caseIndex`, from 0): `world` is the world of that case (`Session.start`, the world the incident starts from, plus the changes of the case: `caseWorld`), and `sent`, `history`, `hintsShown` and `named` (the options of the cause question named so far in this case) belong to the case. `currentCase` is the case, `sendingOf` whatever offers the send chips now (the send incident, or the case), `hintsOf` the hints in play and `canAskHint` whether one is left to show (not once the case is closed). The action `nameCause` (`{ index }`) names an option: a wrong one is kept in `named`, so its feedback shows and the player tries another; the right one is kept too, and it closes the case (`closeCaseIfDone`) when the case has nothing else to ask, pushing `{ picks, hints }` onto `caseResults` (`picks`: the options named in order, the last the right one; `hints`: those asked in the case). A case with a fix (`CaseSpec.fix`: tables to edit and tasks that must hold) closes only when both are true, the right cause named (`causeNamed`) and every task of the fix holding in the packets sent since the world last changed (`failingFixTaskIds`, which reads `sent` as a send incident's tasks do), in whichever order the player did them: `closeCaseIfDone` runs after `nameCause` and after every send, and does nothing in a case already closed, so a send in a closed case adds no second result. While the right cause is named and the fix is pending no other cause can be named, so the right one stays the last of `named` and a hint asked then still counts in the case. Closing the last case, by either way, ends the incident as below. The player edits the world in a case with a fix with the same three actions as in a send incident (`placeEntry`, `removeEntry`; `setSetting` finds nothing to set), on the tables of the fix of the case in play and on no other (`canEdit`, which the cards of the tables read too, so a table is read only exactly when the session would refuse the edit: a send incident that is open, or a diagnose in a case with a fix that is not closed; `applyMove` and `placementProblem` take the case as their last argument); a change of the world clears `sent` and `history` and keeps `named`, `hintsShown`, the send number and the clock, and a case already closed or with no fix edits nothing. A repair is worth only inside its case: `nextCase` builds the world of the next one from `Session.start` plus its own changes, so nothing the player edited carries over, and it drops the refused entry kept in `entryProblem`. The case stays on screen, closed, so the player reads the feedback of the right option; `nextCase` then opens the next one (its world; `sent`, `history`, `hintsShown` and `named` start empty, so the first TCP or UDP packet of the case leaves from the first source port again; the send number goes on counting). The last case closed ends the incident: the phase goes to `explaining` and the middle star is settled (`noHintInAnyCase`), and `showResult` takes it to `result` with no explanation chosen. An option out of range, one already named, any naming in a closed case or once the right one is named, `nextCase` before the case is closed, and `submit`, a rule, a card answer, a setting, a table entry, a wait or an explanation choice do nothing. The explained star is `everyCauseAtFirstTry` (every case closed, each with the right option as the first one named); `firstTry` is the same fact for one case, and the result card uses it for the cases that missed (`caseSummary`).
- No real clock: the session changes only with player actions, and the only time it knows is `Session.clock`, which `wait` moves; nothing here reads the system clock, storage or the DOM.
- Not here: network rules (`src/engine/`), incident content and the world chain (`src/levels/`), drawing (`src/scene/`, `src/ui/`). The tests that play a whole chapter are in `chapters/` (`chapter-1.test.ts`, `chapter-2.test.ts`, `chapter-3.test.ts` and `chapter-3-dead-ends.test.ts`), because this folder is full.
- May import: `@/engine`, `@/copy`, `@/levels`. Files inside import each other directly (`./x`, `./view/x`, `@/game/<folder>/x`).
